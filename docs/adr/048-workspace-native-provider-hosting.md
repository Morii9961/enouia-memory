# ADR-MEM-48 — Hosting native Provider dispatch in the workspace Core

Status: Adopted for the MV-7 host integration; real-account activation and Runtime acceptance remain pending.
Date: 2026-10-10

[ADR-MEM-47](047-explicit-provider-dispatch.md) added native OpenAI/Anthropic text dispatch as a Rust API and left the workspace on Mock. Runtime hosts Memory's local client by embedding `enouia-memory-workspace` ([ADR-MEM-45](README.md)). Runtime must not build its own Provider path around Memory's Vault, so the Core gains the host-facing half. Lifecycle, worker cancellation/join and plan custody already live in the Core and are reused.

## Decision

1. **Injected, native-only setup.** `Workspace::set_native_provider(Some(NativeProvider))` enables native sending. It carries a `Transport`, a `SecretStore`, one `NativeDestination` per API (exact model plus owner-verified `ProviderCapabilities`), a per-Session `Quota` and `Limits`. Runtime passes `HttpsTransport` and the Windows `CredentialStore`; tests pass fakes. Nothing is inferred from a subscription or model name, and keys never cross the page. Without a setup, every external command returns non-retryable `provider_unavailable` / `provider.not_configured`, the status row stays `local_mock_only`, and Mock is unchanged. The reference shell never configures it. `set_native_provider(None)` removes the setup. Reconfiguring refuses with `busy` / `provider.call_running` while a send is running, and it discards held plans and prepared calls.
2. **Seven page commands** (workspace IPC v1, 43 commands): `provider_status` (configured APIs/models/capabilities, owner grants; no keys); `egress_grant_plan` and `egress_revoke_plan` (hold an opaque plan, return its exact canonical bytes and hash); `provider_confirm` (confirms a held grant, revocation or interruption plan by exact hash; a wrong hash keeps the plan; a confirmed plan replays its result); `external_prepare` (write: saves the input, compiles for the exact destination and returns the exact HTTP body, endpoint, wire hash and estimate, without reading a credential or sending); `external_send` (write, long-running: the page confirms the exact wire hash; the Core records the single-use Egress approval and sends once on an operation worker); `external_interrupt_plan` (plans a local close of an unknown admission). Grants cover all projects and the Session/memory record kinds up to `normal` or `private`, for Answer and ContinueSession only. Extraction stays native and inactive in the host.
3. **One attempt, observable state.** A prepared call is single-use and expires after 15 minutes, which is the approval lifetime. A keyed `external_send` retry returns the same operation; a new key cannot reuse a consumed call. Approval and admission happen before the worker sends. The operation result carries the dispatch, finish and reported usage. `session_detail` gains `invocations`, the Session's Provider ledger without wire text or keys, so a page can show unknown, failed or length outcomes after any interruption.
4. **Lifecycle.** Each open Vault has its own native `enabled` flag. Close and lock turn it off before cancelling and joining operations, so a late result cannot publish into a closed Vault. It stays `outcome_unknown`, and the owner closes it with an interruption plan after reopening. Interruption is refused while that dispatch's worker runs. Plans and prepared calls are forgotten on close, lock and reconfiguration.
5. **The send worker** is a plain `std::thread` from the Core's operation table, outside any Tokio context, as native HTTPS requires.
6. **Correction.** The Core chose "the first Policy record" as a new Session's access policy. Egress grants are Policy records too, so it now selects the genesis default policy explicitly.

## Consequences

The Core now depends on `enouia-memory-provider`, which brings its pinned HTTP/TLS crates (`reqwest =0.13.5`, `rustls =0.23.45`, `rustls-platform-verifier =0.7.1`, `tokio =1.53.1`) into Runtime's build. The lower Core crates (Vault, Context, Govern, Index, Import) still do not depend on Provider. The Provider crate's source joins the Runtime surface manifest.

The page is the owner's trusted Windows surface, the same trust that already confirms review and purge plans by hash. The exact wire body may contain private memory text and is shown only to that page. Credential entry and removal stay native host actions; `CredentialStore::write/delete` are unchanged and need a quiesced setup (`set_native_provider(None)` after cancelling sends).

Evidence is synthetic: fake transports and secrets through the page channel. There is no real account, HTTP, credential store or Runtime UI acceptance. MV-7's real two-Provider smoke remains the stage exit gate. MV-8 is not started.
