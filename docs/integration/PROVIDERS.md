# Native text Provider integration

Implemented in `crates/enouia-memory-provider`; [ADR-MEM-47](../adr/047-explicit-provider-dispatch.md) defines the boundaries. This is a Rust native interface for a future host adapter. Existing workspace IPC, the reference shell and Runtime's current product UI have not been switched to real calls.

## Prepare and inspect

Use `Api::OpenAiResponses` or `Api::AnthropicMessages`, then `Api::binding(model)` with an explicitly chosen model. Supply account-verified `ProviderCapabilities`: text/streaming support, context/output limits, counting method and verification timestamp. No model name, account access, API key or price is assumed from a subscription. This implementation accepts `TokenCounting::Estimated`; unknown or unsupported counting is refused. The input estimate covers full wire UTF-8 bytes and a safety margin. It cannot promise an exact tokenizer/context-window boundary; a server context-limit rejection is a terminal failure.

`policy::plan_grant(vault, owner, trusted_surface, resources, purposes, bindings)` produces an opaque plan. Display `inspect()` and require the matching `hash()` in `policy::confirm`. Grant/revocation plans bind their original local Vault ID and physical root privately, as well as owner, trusted surface, pinned history and expiry. A copied/restored Vault retaining the same IDs/history cannot use another root's confirmation; prepare and inspect a fresh plan there. Root paths are not serialized into policy/approval records or displayed inspection bytes. One grant may name both supported APIs, each with its exact model. A native revision review using `Decision::AcceptWithEgress` binds a memory to that grant. Reading a memory locally and authorizing it externally are separate decisions. `plan_revoke` makes a shown revocation; pending capsules fail after it is confirmed.

Save the input with existing `session::save_input`, rebuild/update the index and call `compiler::compile_for_destination` with the exact external destination. The saved capsule includes the input event and evidence set. Construct `VaultAdapter` with that input event, authenticated Vault owner, explicit enabled flag, and `Quota`. Call `prepare_saved` with `Limits` and `CallOptions`. Inspect `PreparedCall::inspect().body()`, endpoint, binding and hash. The stored logical request digest and actual HTTP body digest are distinct; neither includes credentials.

For private resources call `VaultAdapter::approve(call, inspected_wire_hash, trusted_surface, nonce)` after the native owner confirms the displayed body. Approval expires after 15 minutes and is consumed by admission; changing model, output limit, body or evidence requires a fresh preparation/inspection. This does not permit highly sensitive content.

## Send and recover

Instantiate `Client` with `HttpsTransport`, native `CredentialStore`, and the same `VaultAdapter` as guard/journal. Run its synchronous `send` on a dedicated native thread outside **any entered Tokio context** and off the UI thread; a Tokio blocking-pool worker may still carry an entered context and is not supported by this conservative native policy. Pass the exact inspected wire hash and a cancellation handle. The only HTTP endpoints are the two fixed official origins. There is no proxy inference, redirect, automatic retry or fallback.

Native HTTPS owns an explicit Ring `rustls::ClientConfig` instead of installing or inheriting a process-wide crypto default. It uses the same platform certificate/hostname verifier as pinned reqwest through `rustls-platform-verifier::BuilderVerifierExt`, and explicitly uses HTTP/1.1 ALPN/client mode. Existing HTTPS-only, no-proxy/redirect/retry and timeout rules remain. A host's unrelated global crypto configuration is preserved and cannot choose this client's crypto provider. The direct verifier dependency pins the already-locked `0.7.1` package; no dependency version was upgraded. The pinned Rustls/reqwest/verifier sources were checked locally, including reqwest's existing verifier construction and its [preconfigured TLS interface](https://docs.rs/reqwest/0.13.5/reqwest/struct.ClientBuilder.html#method.tls_backend_preconfigured); the [verifier project](https://github.com/rustls/rustls-platform-verifier) documents platform trust validation. Keep these exact compatible versions together because preconfigured backend types must match reqwest's Rustls version. Offline client construction does not prove live handshake, trust-store or server acceptance.

`Transport::preflight` is a local, side-effect-free execution-context check with a default allowed implementation for existing/custom transports. `Client::send` invokes it before guard/credential access or admission. Native HTTPS refuses an entered Tokio context with nonretryable `InvalidRequest`, avoiding the nested-runtime panic described by the pinned [Tokio 1.53.1 `Runtime::block_on`](https://docs.rs/tokio/1.53.1/tokio/runtime/struct.Runtime.html#method.block_on). Direct `HttpsTransport::exchange` applies the same check before creating its own runtime. This setup failure does not consume approval, archive a request, reserve budget or create an invocation, so the ordinary exact call remains subject to the usual guards when the host explicitly submits it from a supported worker. No automatic resubmission or transport switch is added.

After the secret store returns, `Client` invokes local `Transport::validate_secret` before audit/admission. Native HTTPS reuses its existing UTF-8, nonempty, at-most-4096-byte and no-ASCII-control rules; malformed local credentials return nonretryable `Unauthenticated` without consuming private approval or budget. Direct exchange checks the same shape before creating a runtime. The check never retains/logs the secret or contacts a server, and does not establish account access or whether a well-formed key is valid. Custom transports keep an allowed default for opaque/binary credentials. Updating local setup alone adds no automatic send; usual inspection/approval/freshness gates still apply.

After an admitted request receives a response, native HTTPS checks status and expected JSON/SSE media type through pure `HttpsTransport::validate_response_head` before reading body bytes. HTTP 401 becomes `Unauthenticated` and 403 becomes `PermissionDenied`, following the [OpenAI SDK status types](https://developers.openai.com/api/reference/typescript#handling-errors) and [Anthropic error definitions](https://platform.claude.com/docs/en/api/errors). Other non-success statuses, redirects and wrong/missing media types remain `ProviderUnavailable`; ambiguous rate-limit/spend/service causes are not inferred from raw messages. Error bodies and arbitrary headers never enter the structured error, chunks or saved response. This remote refusal has already consumed one admission/approval and retains its reservation and failed terminal, unlike local credential-shape refusal before admission. `Client` marks the failure nonretryable; correcting setup still requires a new explicit input, with no resend/fallback/refund. The pure helper supports offline host harnesses but establishes no authorization or live account compatibility.

Admission refuses any input already ended by a local completed, cancelled or failed turn, even if no native Provider ledger exists. An old prepared call cannot restart an input cancelled locally or already answered by Mock. `InvocationJournal::claim` returning false means an attempt already exists or that turn is closed; neither permits HTTP. No new reservation/archive is created. Save a new explicit owner input to start another turn.

The host must disable `enabled`, signal cancellation and join its worker before clearing Vault-scoped state on lock/close. A disabled adapter refuses preparation, approval, invocation reads, archived inspection, saved responses, local recovery and terminal publication with `VaultLocked`. Reads recheck the flag before returning protected content. An admitted call whose result arrives after disable retains its unknown ledger; disabling does not authorize a resend. These checks do not replace host worker cancellation/join, which prevents work racing lock/close. Authorization and restore gates are checked before admission, during receipt and before final delivery. Stream deltas are saved as partial Session events; polling the Session can show persisted text. A transport EOF without a terminal event is a failure. A `Length` result preserves text but does not complete the turn.

Use `invocations()` for reservations/outcomes, `saved_response(dispatch_id)` for a terminal saved result, and `inspect_saved(dispatch_id)` for the exact archived body. These are owner-only Vault reads and respect freshness/deletion barriers. Native terminal publication uses transport-neutral `session::append_invocation_output`: the response event/content and exact outcome, nullable usage and error metadata enter the existing Vault commit together. Before publication they all remain unknown; after publication they all survive reopening even if the caller received a storage error. Replaying the same terminal key binds that metadata too; changed usage/state is an idempotency conflict. Existing Mock append hashes are unchanged.

`recover_local_outcome` remains available for older terminal receipts saved separately from their ledger. This legacy repair does not send HTTP; it may conservatively recover length as failed and retain unknown usage. Newly published native terminals need no ledger repair. No receipt means unknown; never resend that input event. To choose a different Provider after a known failed attempt, first save a new explicit user turn. No automatic switch is provided.

For an admitted call still unknown after reopening, the native owner may explicitly close that local turn. First stop submissions, cancel and join any worker. On an enabled owner adapter for the original input, call `plan_interruption(dispatch_id, trusted_surface)`, display its `inspect()` metadata and confirm its exact `hash()` through `confirm_interruption`. The private in-memory plan binds owner, local Vault/root, original admission/input and trusted surface, and expires after ten minutes. Wrong owner/root/surface/hash, disabled access and expired plans are refused. Planning never writes, reads credentials or sends; confirmation publishes a local `TurnCancelled` event and `Cancelled` invocation metadata together. Identical confirmation replays the same event. A saved legacy terminal must be recovered instead; this operation cannot overwrite a known reply.

This is a **local interruption**, not proof the remote request was cancelled or free. The immutable admitted Dispatch remains unknown; partial text and original token/monetary reservations remain, nullable usage stays unknown, and the old input can never be resent. After local closure, save a new explicit owner input to continue that Session; its admission still debits the old reservation floor. A caller that never admitted a native attempt can use the existing owner Session cancellation operation; the closed-turn admission guard then blocks any old prepared call. Host controls/UI and actual worker joining remain Runtime adoption duties.

The SSE decoder checks Anthropic's start/block/top-level-delta/stop phases: top-level updates cannot precede message start, interrupt an open content block, conflict on stop reason or reopen blocks. Multiple top-level deltas remain supported, as documented in the [official event flow](https://platform.claude.com/docs/en/build-with-claude/streaming). Usage counters replace cumulative values rather than adding them; omitted/null optional input usage and stop reasons retain the previous known value (see the [SDK delta type](https://github.com/anthropics/anthropic-sdk-python/blob/main/src/anthropic/types/raw_message_delta_event.py) and [usage type](https://github.com/anthropics/anthropic-sdk-python/blob/main/src/anthropic/types/message_delta_usage.py)). Any parser, limit or text-persistence callback failure permanently fails that decoder: later `push`/`finish` cannot turn it into a successful result, even if a valid terminal had arrived before an invalid trailing event.

Line framing accepts LF, CRLF, standalone CR and mixtures, including a CRLF pair split between byte callbacks. One UTF-8 BOM is stripped only at the start of the stream; the same character inside response text is preserved. These framing rules follow the [WHATWG event-stream grammar and interpretation](https://html.spec.whatwg.org/multipage/server-sent-events.html#parsing-an-event-stream). A final event still needs its blank line and a valid Provider terminal; EOF, a BOM or a line ending cannot invent completion. Known JSON/metadata validation, event/body ceilings, failure latching and exact text persistence remain. This adopts framing rules only, without browser EventSource reconnect, redirect or retry behavior.

Nonempty output text is preserved exactly, including standalone spaces, tabs, line breaks and whitespace-only terminal responses. Empty SSE deltas do not invoke the persistence callback or consume a chunk sequence. Valid completed/length terminal responses with no visible text still save an empty content object and the exact finish/usage together; no partial chunk is invented. Whitespace-only user inputs and empty stored chunks remain refused. Empty visible text does not imply missing usage, failure, or a new send permission; display the saved finish and reported counters explicitly.

Reported input usage is a total token count. For Anthropic, sum uncached `input_tokens`, `cache_creation_input_tokens` and `cache_read_input_tokens`, as defined by the [official Message usage](https://github.com/anthropics/anthropic-sdk-python/blob/main/src/anthropic/types/message.py); nested cache-creation details are a breakdown of that creation count. OpenAI's `input_tokens_details` is a breakdown of `input_tokens`, so it is not added again ([Responses usage](https://developers.openai.com/api/reference/resources/responses/methods/retrieve)). Streaming preserves and updates Anthropic's optional cache counts before normalizing the final total. Missing/null usage remains unknown; present counts must be nonnegative integers within the contract's safe integer range, and summed totals must fit too. Malformed counts fail before terminal completion publication. These totals do not provide cache-specific billing or a verified invoice cost: reservations still use the caller's explicit rates and remain conservative/non-refunding.

Anthropic start/delta usage is checked immediately, and each merged running total is checked again. The [official stream protocol](https://platform.claude.com/docs/en/build-with-claude/streaming#event-types) defines top-level token counts as cumulative. Every known input/output/cache-creation/cache-read component must therefore stay equal or increase; a smaller update fails even if another component grows enough to hide it in the normalized total. Missing/null fields retain their previous values. Failure keeps the last completely validated report for later quota admission and latches across corrected updates or a stop event; no refund, completion or resend permission is created. Malformed updates cannot be hidden by a later valid cumulative value. The accumulator always stays an object; absent/null initial usage remains unknown and cannot cause a panic when a later counter arrives. A top-level delta requires an object, and present non-null stop reasons must be strings. Unknown future event kinds/fields retain their existing forward-compatible handling; known malformed fields latch the decoder failure.

The adapter requires OpenAI's terminal event kind and nested response status to agree: `response.completed` carries `completed`, while `response.incomplete` carries `incomplete`. This native consistency rule follows the distinction between the official SDK's [completed event](https://github.com/openai/openai-python/blob/main/src/openai/types/responses/response_completed_event.py) and [incomplete event](https://github.com/openai/openai-python/blob/main/src/openai/types/responses/response_incomplete_event.py), checked on 2026-10-09. A contradiction latches a local protocol failure before completion/length publication; saved partial text remains, the input is not resent, and later correct metadata cannot repair that failed decoder. Matching incomplete responses still require the supported output-token limit reason.

`Quota` bounds Session attempts and token admission, with optional `PriceLimit` in integer micro-USD per million tokens. Each earlier attempt debits the higher of its whole token reservation and its known reported input/output sum. Missing counts stay unknown in the stored ledger; they never refund the reservation floor. Thus a known estimate overrun blocks further admission at an insufficient ceiling, while lower usage does not automatically release allowance. Saved extraction token ceilings constrain this same debit. Original reservations remain immutable. Monetary admission still uses stored cost reservations at explicitly supplied rates, without inferring historical or cache-specific billed prices. This is a local admission limit, not a billing statement or global/account quota. The host must provide rates explicitly and implement any broader account budget.

For interrupted streams, `Decoder::observed_usage` exposes the last fully validated reported counters. Anthropic start/delta updates are normalized only after the update and merged total validate; OpenAI usage is retained after a valid, text-matching terminal response. A later malformed event, transport failure or local cancellation cannot erase those counters or promote the call to completion. `Client` passes them to `InvocationJournal::finish_failure`; `VaultAdapter` publishes nullable counters with the failed/cancelled terminal in one existing atomic commit. They may be partial reports, not final billing totals, and missing values are never guessed. Later token admission applies the same reservation-floor/known-sum rule. Custom journals keep their prior failure behavior by default; a custom budget-aware journal must override `finish_failure` to retain these counters. No failed/cancelled completed response or resend permission is created.

## Credentials and resources

The Windows store targets are fixed: `Enouia.Memory.Provider.openai` and `Enouia.Memory.Provider.anthropic`. Credential writes are native-only. Read/write/delete functions and HTTPS transport are implemented but deliberately not exercised with a real account in this implementation run. Keys do not enter page IPC, Session objects, fixtures or logs. Non-Windows native credential access is unsupported; another native SecretStore can implement the port.

For an explicit trusted native setup action, `CredentialStore::delete(name)` removes only one of those two exact generic credential entries. It validates the name before any OS call and never reads the stored key. Microsoft [CredDeleteW](https://learn.microsoft.com/en-us/windows/win32/api/wincred/nf-wincred-creddeletew) reports an absent target as `ERROR_NOT_FOUND`; success or confirmed absence both return `Ok`, making repeated removal idempotent. Other OS failures return the existing retryable local `StorageFailed`; the method does not retry automatically. Unsupported platforms return `ProviderUnavailable`, while invalid targets are always refused. If removing setup for an active adapter, stop submissions, cancel/join its workers and explicitly disable it before this native action; a worker may already hold a copied key. Local removal neither revokes the remote key nor cancels an admitted call, changes its ledger/reservation, or authorizes a resend. Keep this action out of page key material/automatic lock or disable handlers. The implementation is compiled and fake-driver tested only; no actual credential entry was read, written or removed during validation.

The owner deferred real smoke calls. Both adapters are validated only with synthetic Vaults and fake transports. Optional candidate extraction is implemented as an explicit native flow and remains inactive until the host exposes and enables it. No MV-8 Host/MCP work starts here.

## Optional extraction

`extraction::create` saves an owner-selected `ExtractionOptions` job without HTTP. Select 1–16 exact Source revisions and UTF-8 byte ranges; each range is at most 32 KiB, their combined size at most 64 KiB. The resolved source content and snippet hashes, exact API/model, native-selected subject, `extract-text-2` prompt version, candidate limit (1–32), pending backlog ceiling (1–500), token reservation ceiling and optional integer micro-USD cost ceiling are immutable. Storage validation binds the job to its saved input, source hashes and existing candidate IDs; scoped validation loads all selected revisions. Reusing the creation key with changed input is refused. Imported locators require the complete raw object and refuse objects over 64 MiB before allocation. This limit never silently truncates a source.

The prompt carries the actual speaker role and evidence class. The extraction compiler selects source evidence and the saved input, without searching unrelated canonical memories or identities. SourceRead and destination ProviderSend grants, sensitivity restrictions, inspection, private per-request approval, quota, audit and one-attempt admission still apply. Construct `VaultAdapter` with the job's `input_event_id`, then `extraction::prepare`; inspect/approve/send with the ordinary native flow. A disabled adapter refuses preparation and candidate application. Admission also rechecks paused state, the exact job binding and Extraction purpose. Saved job budgets cap the caller’s Session quota; a saved monetary cap requires explicit price rates and cannot be bypassed by restoring a higher default quota. Input safety margin is included in both token and price reservations.

After a completed saved response, `extraction::apply_next` validates the entire strict JSON candidate envelope before publishing anything. Only facts and preferences are accepted in this version. Claims need a literal quote inside a selected snippet; the native subject and exact source evidence are assigned independently of the model. Length-limited, failed, cancelled and unknown outcomes cannot become extraction candidates. All claims start uncertain and pending with ModelExtraction origin/run provenance; the existing owner review decides canonical acceptance. Literal quotation proves source containment, not the truth of the model's paraphrase.

Preparation, preview and application all require an adapter bound to the job's original `input_event_id`. Application checks this before ready/paused/completed handling, including its read-only completed replay. An adapter for a later input in the same Session returns `PermissionDenied` without advancing candidates/cursor or returning the old job's completed replay. Reconstruct the adapter from the saved job input when resuming; the active conversational input is not a substitute. Correctly bound completed replay remains read-only and no new HTTP permission is created.

One call applies at most one candidate and then saves the cursor in `SessionRecord.extraction_jobs`. `set_paused` controls local application; resume reads the same saved response and never calls HTTP again. A crash between candidate publication and cursor persistence recovers the original receipt/ID even if the pending backlog is now full or the owner has reviewed the candidate. New publication uses the same pinned head as the pause/backlog check. Identical reviewed claims against unchanged source content/evidence class are suppressed and recorded as null cursor entries; materially changed evidence may enter review again. Pending duplicate fingerprints reuse the existing candidate. Candidate evidence preserves its existing whole-source locator; the precise selected offsets/quote remain traceable through the saved job/request/response.

Pause/resume controls pin the Vault head before validating the job and sources. Cursor/control changes during that validation cause `RevisionConflict` without publishing the stale control; the host must refresh the job before issuing a new explicit control. A delayed operation cannot silently adopt the later progress view. Completed jobs remain protected by the existing immutable-history rule, and repeated completed application remains read-only.

New jobs use `extract-text-2`: the inspected input includes exact selection offsets and source occurrence/capture time, precision and known/unknown branch alongside speaker role and evidence class. The prompt distinguishes source occurrence from claim validity and archival time; it preserves uncertainty, negation, conditions and unknown branches/times. This metadata does not independently prove a model claim. Existing `extract-text-1` jobs remain valid and prepare/apply their original saved input without rewriting it. A changed version or selection under a previously used create key requires a new explicit key; no live request is silently upgraded. Earlier strict readers accepting only version 1 reject version-2 jobs and need a pin update.

Preference claims additionally require the selected Source's stored evidence class to be `user_statement` or `user_confirmation`. Model claims, summaries, external observations and unknown evidence cannot directly produce user preference candidates, even when agent text claims user consent. This rule applies to validation/preview/application of both prompt versions; an invalid later preference refuses the entire response before any proposal. Fact suggestions may remain pending with their actual source evidence class and uncertain epistemic status. The adapter never silently converts invalid preferences to facts, upgrades evidence, or accepts either kind automatically.

Call `extraction::preview(adapter, run)` to inspect an already completed saved response locally. It validates every claim/quotation before returning any item, including while the job is paused. Each item separates the original model proposal from the latest recorded candidate revision, status and conflicts, and supplies the literal quote, complete selected snippet (including qualifiers outside the quote), source revision/hash, selected range, exact UTF-8 byte range within resolved Source text, speaker role, evidence class, sensitivity, source timestamps/precision and known/unknown branch. Repeated quotes use the first occurrence inside the selected slice. These offsets are not raw-export offsets and do not replace the candidate's stored locator. A reused candidate keeps its existing evidence. `AwaitingCursor` means no cursor entry is recorded yet, including a possible publication/cursor crash gap; `Suppressed` means a recorded null entry. Preview does not create a candidate, advance a cursor, send HTTP or approve anything, and refuses disabled/unauthorized handles, unavailable results, erased/stale sources and a changed pinned view. Its native types are private host views, not a new persisted or IPC contract.

Deleting source evidence with dependents includes the saved extraction input before a capsule or Dispatch exists, plus ordinary request/response dependents after admission. Jobs retain non-content IDs, hashes and progress as deletion-safe metadata; erased input/source reads fail. Extraction jobs are optional and omitted when empty. Populated jobs, like populated Provider ledgers, require new strict Session readers. The native host must stop extraction workers before closing/locking the Vault; no worker or product toggle is created here.

## API sources checked during implementation

- [OpenAI Responses create](https://developers.openai.com/api/reference/python/resources/responses/methods/create): text input, streaming, output cap, `store` and `truncation`.
- [Anthropic Messages create](https://platform.claude.com/docs/en/api/messages/create) and [streaming](https://platform.claude.com/docs/en/build-with-claude/streaming): version header, system blocks and typed SSE lifecycle.
- [reqwest 0.13.5 ClientBuilder](https://docs.rs/reqwest/0.13.5/reqwest/struct.ClientBuilder.html): fixed TLS transport and explicit request policies.
- Microsoft [CredReadW](https://learn.microsoft.com/en-us/windows/win32/api/wincred/nf-wincred-credreadw) and [CredWriteW](https://learn.microsoft.com/en-us/windows/win32/api/wincred/nf-wincred-credwritew): named native credentials.
